## What this proposes

This document proposes building a browser-based, 12-character guessing game ("Guess Who? — Decisions API Demo") to showcase bounded natural-language classification using the experimental Decisions API (`window.DecisionModel` or a verified, explicitly labeled local polyfill). Players submit free-form yes/no questions about a randomly chosen secret character, and the app maps structured model decisions against the character's explicit facts into fixed UI responses ("Yes", "No", "Not enough information", or rephrase/card-selection guidance) while leaving card elimination manual. Alongside the playable board, an inspection view surfaces engine identity, selected labels, probabilities, confidence, inference latency, and optional spoiler-gated context for live technical demonstrations. Implementation is structured into four sequential milestones—proving a real runtime integration first, creating the 12 profiles and a 40+ case evaluation suite, building the playable round, and adding showcase/accessibility polish—while forbidding silent generative-LLM, keyword, or mock fallbacks.

## How the existing system works, per this document

The document describes no existing application codebase, framing the architecture (a suggested TypeScript, Vite, and React stack "if no repository conventions exist") as an untested greenfield proposal rather than changes to a running system. With respect to the required browser capability, it states only that the Decisions API is currently an early explainer proposal that has not been approved to ship in Chrome. According to that explainer summary, the proposed API entry point is `window.DecisionModel`, which uses schema-based session creation and `decide(input)` calls returning labels, probabilities, and confidence, though no runtime implementation has been verified for this plan.

3. **Discrepancy Description & Rationale**: Line 11 notes that `window.DecisionModel` has not been approved to ship in Chrome, and line 17 permits "An explicitly documented Decisions API-compatible local polyfill ... after verifying its contract and runtime behavior." However, lines 18 and 270 forbid *silently* substituting the Prompt API or generative APIs, while line 300 forbids marking integration complete based on "a compatible-looking interface, or an unrelated AI service." Because any polyfill in an unsupported browser inherently provides a compatible interface backed by another runtime or local model, an implementer executing Phase 1 cannot tell what qualifies as a legitimate local polyfill (e.g., whether only an official explainer-provided polyfill qualifies, whether a local non-generative classifier wrapper qualifies, or whether an *explicitly labeled* local Prompt API polyfill is permitted) versus triggering the mandatory Phase 1 blocker exit (lines 20, 225).

#### Finding 3 — Undefined "interpretation confidence" across a two-decision schema
1. **Severity**: `[Major]`
2. **Affected Scope**: `## 5. Decision design` / `### Proposed questions in the decision schema` & `### Application behavior` ([guess-who-project-plan.md](../guess-who-project-plan.md#L106-L110), [guess-who-project-plan.md](../guess-who-project-plan.md#L122-L131)) and `## 6. User interface` / `### Game and demo views` ([guess-who-project-plan.md](../guess-who-project-plan.md#L174)); concept: `interpretation confidence`.
3. **Discrepancy Description & Rationale**: The proposed schema defines two distinct choice decisions (`question_kind` and `answer`, lines 108–109), yet lines 123 and 174 refer to a single "interpretation confidence" / "Reported confidence". In addition, step 4 ("Apply the question-kind policy first", line 122) runs *before* step 5 ("If interpretation confidence does not meet an evaluated threshold, ask for a rephrase", line 123). A fresh reader cannot tell whether the confidence threshold gates `question_kind` (before acting on `identity_guess` or `trait_question`), gates `answer` (asking the player to rephrase even when `question_kind` is high-confidence `trait_question` if `answer` confidence is low), or requires separate thresholds per decision ID.

#### Finding 5 — Ambiguous evaluation metric denominators, dataset sizing, and acceptance-gate semantics
1. **Severity**: `[Major]`
2. **Affected Scope**: `## 9. Implementation milestones` / `### Phase 2 — Define content and evaluation` ([guess-who-project-plan.md](../guess-who-project-plan.md#L232-L236)) and `## 10. Validation and acceptance criteria` / `### Tests and evaluation` ([guess-who-project-plan.md](../guess-who-project-plan.md#L282-L283)); concepts: `per-label accuracy`, `clarification rate`, and `Proposed demo target`.
3. **Discrepancy Description & Rationale**:
   - Line 282 requires reporting `per-label accuracy` and `clarification rate` without specifying whether `per-label accuracy` is measured on raw `question_kind`/`answer` model outputs or post-confidence-gate app outcomes, nor whether `clarification rate` uses *all* held-out cases as its denominator (which include deliberately ambiguous and invalid prompts per line 232 that *should* produce clarifications) or only valid single-trait questions.
   - Line 283 places quantitative thresholds ("at least 90% accuracy among accepted factual answers on held-out cases, while accepting at least 70% of valid single-trait questions") inside a required acceptance-criteria checkbox (`- [ ]`), then immediately states "These are goals, not measured results; show sample sizes and all failures," leaving ambiguous whether missing 90%/70% blocks sign-off or passes so long as failures are reported.
   - Line 232 sets a floor of 40 total cases across seven categories (`yes`, `no`, `unknown`, paraphrases, negation, ambiguity, invalid requests) that must then be split into threshold-tuning and held-out sets (line 233) with no minimum held-out count specified, which could leave too few valid held-out cases for 90%/70% percentages to be meaningful.

#### Finding 7 — Unresolved tension between illustrated portraits, visual questions, and biography parity
1. **Severity**: `[Nit]`
2. **Affected Scope**: `## 4. Character content` ([guess-who-project-plan.md](../guess-who-project-plan.md#L55), [guess-who-project-plan.md](../guess-who-project-plan.md#L68), [guess-who-project-plan.md](../guess-who-project-plan.md#L71-L72)); concept: `visual questions`.
3. **Discrepancy Description & Rationale**: Line 55 requires public biographies and model facts to "describe the same information," while line 72 states "Only support visual questions if corresponding attributes are explicitly encoded and match the artwork." Because players in an illustrated *Guess Who?*-style game naturally ask about visible portrait features (glasses, hats, hair), leaving undecided whether visual traits are intentionally excluded (producing `"Not enough information"` for visibly obvious features) or encoded (forcing every public biography to enumerate physical appearance details to satisfy line 55) pushes a core content-design choice onto implementation.
